概念二

大模型上下文

模型在一次调用中能够看到并据此生成回答的全部信息集合，而不是模型永久记住的一段文字。

上下文包含什么

系统指令

规定角色、目标、限制和输出格式，通常具有较高优先级。

用户消息

本轮问题以及用户提供的约束、示例和偏好。

历史消息

对话前文、工具调用和工具返回结果。

外部资料

检索结果、文件片段、数据库记录或多模态输入。

Token 与上下文窗口

模型处理文本时使用 token，而非简单按字符计数。上下文窗口是单次请求可容纳的 token 上限，通常包括输入与预留的输出空间。

可用输入空间 = 上下文窗口上限 - 输出预留 - 其他开销
窗口越大不代表模型一定能等质量地利用所有内容。无关信息过多会增加成本，并可能降低对关键内容的注意力。

上下文工程

上下文工程是有意识地选择、压缩、排序和组织模型看到的信息，使其足够完整又不过载。

  1. 选择：只放与当前任务相关的材料。
  2. 排序：把任务、约束和关键证据放在清晰位置。
  3. 压缩：总结旧对话，保留决定和未完成事项。
  4. 检索：从知识库取回最相关片段，而不是塞入全文。
  5. 验证：检查资料来源、时间和冲突。

上下文、记忆与知识库

概念含义生命周期
上下文当前请求实际提供给模型的信息通常只在当前调用有效
记忆从过去交互提炼的用户或任务信息跨调用保存，需可管理
知识库外部文档、数据和检索系统独立于模型更新

常见问题

上下文太长

分层摘要、滑动窗口、按任务检索，避免无差别追加历史。

关键信息丢失

保留结构化任务状态，明确标出硬约束、截止日期和验收标准。

提示注入

把外部内容视为不可信数据，隔离指令与资料，并限制工具权限。

事实过期

为时间敏感内容标记日期，必要时在生成前重新检索。

一个实用模板

任务：<要完成的结果>
约束：<不可违反的规则>
已知事实：<经过验证的信息>
参考资料：<相关片段及来源>
输出格式：<结构、长度、受众>
验收标准：<如何判断完成>
